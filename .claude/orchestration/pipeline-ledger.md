## 누적 갭 (OEM-A 확인 필요 등 — 여러 Phase에 걸쳐 이월됨, 절대 조용히 해소하지 말 것)

1. **DEGRADED/FAULT 히스테리시스 없음(즉시 재판정)** — OEM 원문 미기재, Phase 1 아키텍처 단계에서 근거와 함께 결정(병렬-상호배타-FAULT우선). 상세설계에서 재확인 후 채택.
2. **source_timestamp_s 상한/단조성 판정식 미확정** — OEM 원문 미기재. 하한(0.0)만 검증됨.
3. **경고코드(reason_code) 실제 카탈로그 미확정** — OEM-IF-006에 정의 없음. 현재 "정의된 타입의 비공백 값" 기준으로만 판정.
4. **SWR-008(crash_status PENDING 처리)은 추론 요구사항** — OEM-SR-001 원문에 직접 기술 없음, OEM-A 확인 필요.
5. **SWR-006의 override 실제 출력 전환 여부 미기재** — OEM-FR-003 수용기준은 "override 상태/이유코드 생성"만 요구, 실제 RELEASE 전환은 원문 미기재. [SWE.6 재확인, 2026-09-19] `assembleCandidateCommands()`는 override 성립 시에도 억제 후보를 제외할 뿐 별도 RELEASE 후보를 생성하지 않아, 설계상으로도 override가 출력을 RELEASE로 바꾸지 않는다는 것이 시스템 시험(ST-FUNC-0016)에서도 재확인됨.
6. **SWR-006의 ASIL B/QM 혼합 분류** — OEM 추적성 힌트가 OEM-SR-002(ASIL B)와 OEM-FR-003(QM)을 SWR-006 하나로 묶음. 아키텍처에서 ARC-0012로 격리했으나 근본적으로는 재검토 여지가 있음.
7. **releaseReRequested 채널(ARC-0012 입력)이 실제 신호에 미연결** — OEM-FR-001(운전자 명령, Phase 4 예정) 분석 전까지 placeholder(항상 False). [SWE.6 재확인, 2026-09-19] 시스템 경계(`InputValidationAdapter.handleCycle()`)에는 이 채널에 대응하는 원시 입력 필드 자체가 없어(`RawCycleInput`에 재입력/해제요청 필드 없음), SWR-006(a)의 "10초 이내 재입력 시 override 성립" 수용기준을 시스템 수준에서 재현할 방법이 전혀 없다 — ST-FUNC-0016(ENG-SWE6-001/002)이 이를 Fail로 명시 기록(IT-0084가 통합 수준에서 이미 문서화한 것과 같은 한계를 시스템 수준에서 재확인).
8. **ST-FUNC-0009(제안 케이스)의 정식 채택 여부** — 사용자 미확정, 현재 참고용/필수 합격기준 제외로 분리 표기됨.
9. **시스템 테스트 진입점**: `evaluateCycle()`이 아니라 `InputValidationAdapter.handleCycle()`(원시 입력 전체 체인) 사용 — Phase 1에서 근거와 함께 결정, 이후 Phase도 이 방식을 유지.
10. **Phase2 이유코드(leftReasonCode/rightReasonCode, triggeredReasonCodes 등)의 실제 Display/Web 발행 경로 미확장** — SWE.3(상세설계)에서 신규 발견. ARC-0007/IF-0011/IF-0004가 Phase2용으로 확장되지 않아, `IU-0007.publishWarning()`은 여전히 StateResult(state/warningReasonCode)만 변환한다. SWR-005/006/017 등의 "이유코드가 기록된다" 수용기준은 현재 ArbitrationResult/각 IU 반환값 직접 관측으로만 충족(Phase1 warningReasonCode 선례와 동일 전략) — 사용자 대면 Display 발행은 범위 밖.
11. **OEM-IF-002 crash_status 실제 직렬화 타입 미기재** — SWE.3에서 신규 발견. `IU-0001.validateCrashStatusField()`는 문자열 열거형 이름("NONE"/"PENDING"/"CONFIRMED")으로 가정(OEM-IF-002 원문 표기 형태에 근거). 실제 타입이 다르면(예: 정수 코드) 이 함수만 교체하면 되므로 영향은 국소적이나, 확정 전까지 확인 필요.
12. **OEM-IF-001의 gear 필드 미사용** — Phase 3 SWE.1에서 신규 발견. OEM-SWR-001의 어느 OEM-SR/FR 수용기준에도 gear 값을 사용하는 판정 로직이 없다. 자동주행잠금(SWR-003)에 gear(P/N 제외 등)를 함께 사용해야 하는지 OEM-A 확인 필요 — 현재는 vehicle_speed_kph만으로 SWR-003을 정의.
13. **SWR-003/018(LOCK, QM)과 SWR-007/017/020(RELEASE 계열) 간 우선순위 미확정** — Phase 3 SWE.1에서 신규 발견. OEM 원문은 자동주행잠금·ISOFIX강제잠금과 기존 안전요구사항(충돌긴급해제/화재등강제해제/ignition-off해제) 사이의 상대적 우선순위를 규정하지 않는다. `ENG-SWE1-001` 3장에 질적 추정만 제시, 정량적 중재 규칙은 SWE.2 Command Arbiter로 위임. **[Phase 3 SWE.2에서 대부분 해소, 2026-09-20]** Command Arbiter 우선순위 체인을 1=충돌해제>2=접근위험억제>3=화재등해제>4=ignition-off해제>5=ISOFIX강제잠금>6=자동주행잠금으로 확정(`ENG-SWE2-001` 9장) — RELEASE 계열(1,3,4)이 LOCK 계열(5,6)보다 항상 우선한다는 단일 원칙. crash>LOCK계열 관계는 SWR-007(a) 원문("다른 모든 명령보다 우선")의 직접 근거이나, fire>LOCK계열(SWR-017 "강제" 해석)과 ignition-off>LOCK계열(entrapment 방지 취지)은 SW 설계 추론이라 완전한 OEM 확인은 아님. 아래 "SW 설계 재량으로 확정한 사항" 절 참조.
14. **SWR-018(ISOFIX강제잠금)의 해제요청 억제 여부 미기재** — Phase 3 SWE.1에서 신규 발견. OEM-SR-002(접근위험)와 달리 OEM-FR-006 원문에는 "해제 요청을 억제해야 한다"는 문구가 없다 — ISOFIX TRUE인 동안 수동 해제 명령을 허용할지 확인 필요. **[Phase 3 SWE.2 재확인, 2026-09-20]** 해소하지 않고 유지 — ARC-0015는 ISOFIX 후보를 우선순위 경쟁에만 참여시킬 뿐 SWR-005처럼 별도의 명시적 억제 메커니즘을 추가하지 않았다(`ENG-SWE2-001` 9장).
15. **OFF 상태(SWR-020)와 기존 DEGRADED(SWR-013)/FAULT(SWR-021) 상태 관계 미정** — Phase 3 SWE.1에서 신규 발견. 동시성 가능 여부, 우선순위, 상호 전이 허용 여부가 OEM 원문에 없다 — 누적 갭 1(DEGRADED/FAULT 관계 미정)과 동일한 성격의 문제가 3-상태로 확장됨. architecture-design 단계의 상태 머신 설계 시 반드시 결정 필요. **[Phase 3 SWE.2에서 해소, 2026-09-20]** SystemState에 OFF를 4번째 값으로 추가하고 판정 순서를 FAULT>OFF>DEGRADED>NORMAL로 확정(`ENG-SWE2-001` 8장) — 근거: OFF(ignition_on=FALSE)는 형식검증을 통과한 확정적 신호인 반면 DEGRADED는 freshness 초과라는 정황적 증상이라는 성격 차이, OEM-FR-007의 무조건적 어조가 OEM-SR-001(충돌)과 유사. 히스테리시스 필요 여부 등 하위 세부사항은 기존 갭 1과 동일하게 확인 필요로 유지.
16. **SWR-005/006(접근위험 억제, ASIL B)과 SWR-020(ignition-off 해제, QM) 동시 성립 시 우선순위 미정** — Phase 3 SWE.1에서 신규 발견. ASIL B가 QM보다 우선해야 한다는 일반 원칙만으로 자동 결정되지 않으므로 임의로 단정하지 않음. OEM-A 확인 필요. **[Phase 3 SWE.2 재확인, 2026-09-20]** 해소하지 않음 — Command Arbiter는 접근위험(priority=2)이 ignition-off(priority=4)보다 이기도록 잠정 기본값(ASIL B 안전 메커니즘 우선 보존)만 채택했다(`ENG-SWE2-001` 9장) — OEM-A 확인 없이 최종 확정된 것이 아니므로 갭으로 유지.
17. **SWR-003 하강 시 자동 RELEASE 복귀 여부 미기재** — Phase 3 SWE.1에서 신규 발견. 차속이 3km/h 미만으로 재하강했을 때의 동작이 OEM-FR-002 원문에 없다 — 확인 필요. **[Phase 3 SWE.2 재확인, 2026-09-20]** 해소하지 않음 — ARC-0014는 조건 미성립 시 후보를 생성하지 않아 Command Arbiter가 NO_CHANGE로 귀결되고 직전 확정값이 유지되는 것이 현재 설계의 부수 효과이나, 이는 명시적 요구사항이 아니므로 갭으로 유지(`ENG-SWE2-001` 9장).

### 이번 Phase(SWE.3)에서 SW 설계 재량으로 확정한 사항(갭 아님 — 근거와 함께 확정, Phase1 8.2/8.3절과 동일한 성격)

- crash_status/접근위험(좌우)/화재계열 6개 신규 필드가 valid=False일 때의 공통 처리 원칙: "새 능동 후보(LOCK/RELEASE)를 생성하지 않는다"(대체가 아니라 거절) — Phase1 sensor_fault의 "대체" 정책과 의도적으로 다름(근거: ENG-SWE3-001 10.4절).
- ARC-0012(override 판정기) 억제 재시작 시 타이머 리셋 규칙: risk가 False로 전이되면 즉시 리셋, 재진입 시 새 10초 윈도우 시작(근거: ENG-SWE3-001 6.11절).
- IU-0005에서 동일 문에 동일 최소 priority 후보가 2개 이상 존재하는 경우: 설계상 발생 불가한 내부 불변조건 위반으로 간주해 `ValueError`를 발생시키고 IU-0009가 FAULT로 강제(근거: ENG-SWE3-001 5.2절/7장 결정표 I).
- Phase2 candidateCommands와 FAULT/DEGRADED 게이트의 관계: FAULT는 Phase2 후보보다 항상 우선(차단), DEGRADED는 Phase2 후보를 제한하지 않음(근거: ENG-SWE3-001 8.5절 — 단, 이 결정의 실제 안전 적정성은 OEM 근거 부재로 확인 필요로 별도 유지).

### 이번 Phase(Phase 3 SWE.2)에서 SW 설계 재량으로 확정한 사항(갭 아님 — 근거와 함께 확정)

- **Command Arbiter 우선순위 체인 확장**: 1=충돌긴급해제(SWR-007, RELEASE) > 2=접근위험억제(SWR-005/006/009, LOCK) > 3=화재등강제해제(SWR-017, RELEASE) > 4=ignition-off해제(SWR-020, RELEASE, 신규) > 5=ISOFIX강제잠금(SWR-018, LOCK, 신규) > 6=자동주행잠금(SWR-003, LOCK, 신규). 결과적으로 "RELEASE 계열이 LOCK 계열보다 항상 우선한다"는 단일 원칙이 성립(누적 갭 13 대부분 해소). 근거: (1) crash>LOCK계열은 SWR-007(a) 원문("다른 모든 명령보다 우선하여")의 직접 근거. (2) fire>LOCK계열은 SWR-017(OEM-FR-005) "강제로 해제해야 한다"는 문언의 SW 해석(추론, 완전한 OEM 확인은 아님). (3) ignition-off>ISOFIX/자동주행잠금은 SW 설계 재량 — ignition_on=FALSE 시 두 LOCK 요구사항의 전제조건(이동 중/탑승 중)이 소멸하고 OEM-FR-007의 entrapment 방지 취지가 우선 적용되어야 한다는 판단. 이는 Phase 1에서 ARC-0005 설명에 남겨두었던 잠정 확장 골격 순서("...화재등강제해제 > ISOFIX강제잠금 > 자동주행잠금 > ignition-off해제...")를 수정한 것 — 해당 골격은 실제 요구사항 분석 이전의 자리표시자 추정이었음을 명시(근거: ENG-SWE2-001 9장).
- **ISOFIX(5) vs 자동주행잠금(6) 상호 순서**: 두 후보가 항상 동일한 LOCK 명령을 생성하므로 실제 출력에는 영향이 없고(이유코드 보고 우선순위에만 영향), ISOFIX가 더 구체적인 위험 신호(특정 카시트 탑승)이므로 일반적 이동-중-잠금보다 근소하게 위에 배치(영향 미미, 근거: ENG-SWE2-001 9장).
- **SystemState에 OFF 추가, 판정 순서 확정**: FAULT > OFF > DEGRADED > NORMAL(누적 갭 15 해소). 근거: OFF(ignition_on=FALSE)는 형식검증을 통과한 확정적 신호인 반면 DEGRADED는 freshness 초과라는 정황적 증상이라는 성격 차이, OEM-FR-007의 무조건적 어조가 OEM-SR-001(충돌)과 유사(근거: ENG-SWE2-001 8장).
- **state==OFF는 candidateCommands를 제한하지 않음**: DEGRADED와 동일하게 "정보성 상태, 제한 없음" 정책을 적용 — ignition-off 자체의 RELEASE 강제는 ARC-0016의 candidate(priority=4)가 통상적인 우선순위 선택으로 달성하며, Command Arbiter에 별도 게이트를 추가하지 않음(코드 변경 없음, OCP 재확인, 근거: ENG-SWE2-001 8·9장).
- **해소하지 않고 유지한 사항(명시적으로 확정하지 않음)**: 누적 갭 14(SWR-018 해제요청 억제 여부), 갭 16(접근위험 ASIL B vs ignition-off QM 우선순위 — 잠정 기본값만 채택, OEM-A 확인 필요), 갭 17(SWR-003 하강 시 동작 — ARC-0014 후보 미생성의 부수 효과일 뿐 확정 요구사항 아님).

### 이번 Phase(Phase 3 SWE.3)에서 SW 설계 재량으로 확정한 사항(갭 아님 — 근거와 함께 확정)

- **ignitionOnField.valid=False(형식 오류) 시 IU-0003의 OFF 판정 보류**: ENG-SWE2-001 8장이 "확인 필요"로 이월한 갭(a)를 해소 — IU-0003은 이 경우 OFF를 판정하지 않고 freshness/NORMAL 경로(결정표 K 3~4행)로 대체한다. 대칭적으로 IU-0016도 이 경우 releaseCandidate를 생성하지 않는다. 근거: (1) ARC-0016의 IF-0023 오류계약이 이미 "ignitionOnField.valid=False 시 후보 미생성·OFF 미판정"이라고 명시했으므로, IU-0003도 동일한 기준을 적용하는 것이 두 컴포넌트가 동일한 ignitionOnField를 병렬 소비할 때의 내적 일관성을 보장한다. (3) 이미 IU-0009.composeInputValid()가 ignitionOnField.valid=False를 inputValid=False로 판정해 IF-0008 게이트가 전체 사이클을 차단하므로, 이 결정의 실제 위험도는 낮다(근거: ENG-SWE3-001 8.8절).
- **Phase3 신규 3필드(vehicleSpeedField/isofixLeftField/isofixRightField) valid=False 처리**: Phase2가 확정한 10.4절 일반 원칙(신규 능동 후보 미생성, 대체 아님)을 그대로 확장 적용 — 별도의 새로운 정책이 아니라 기존 원칙의 재적용(근거: ENG-SWE3-001 10.7절).
- **IU-0009.composeInputValid()는 Phase3 신규 3필드를 포함하지 않음**: Phase2가 crash_status/접근위험/화재계열 필드에 대해 이미 확정한 결정표 D 원칙(전체 게이트에 신규 필드 valid를 포함시키지 않음 — 무관한 다른 컴포넌트의 정당한 후보까지 차단하는 과도한 결합 방지)을 Phase3 3필드에도 동일하게 적용(코드 변경 없음, 근거: ENG-SWE3-001 7장 결정표 D 재확인/10.7절).
- **StateResult에 changedToOff 전용 플래그를 추가하지 않음**: changedToFault는 Phase1 의미(새로 FAULT로 전이했는가) 그대로 유지하고, OFF 전이를 별도로 추적하는 필드는 추가하지 않는다 — 어떤 SWR도 이를 요구하지 않기 때문(근거: ENG-SWE3-001 4장/13장 구현 경계).
