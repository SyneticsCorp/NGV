# 좋은 테스트 작성하기

출처: [obra/superpowers](https://github.com/obra/superpowers) `skills/test-driven-development/writing-good-tests.md`를 한국어로 옮기고 `unittest`/`unittest.mock` 기준으로 각색했습니다.

**이 문서를 읽어야 할 때:** 테스트를 작성/수정할 때, mock을 추가할 때, 테스트용 정리(cleanup)/헬퍼 메서드를 추가할 때.

## 개요

테스트는 특정한 깨짐(break)을 잡기 위해 존재합니다. 두 가지 원칙이 모든 것을 지배합니다.

```text
1. 모든 테스트는 자신이 잡는 깨짐의 이름을 댈 수 있어야 한다
2. 모든 테스트는 진짜 대상을 검증해야 한다
```

엄격한 TDD는 이 둘을 자연스럽게 만듭니다: 먼저 쓰고 진짜 코드에 대해 실패하는 것을 본 테스트는 이미 "실패할 수 있다"는 것을 증명했고, 진짜 의존성이 느리거나 외부적이라는 것이 확인됐을 때만 mock으로 바꿀 자격을 얻습니다.

## 원칙 1: 깨짐의 이름을 대라

테스트 본문을 쓰기 전에 답하세요: **어떤 프로덕션 코드 변경이 이 테스트를 실패하게 만드는가 — 그리고 그 변경은 버그인가, 아니면 의도된 결정인가?** 테스트는 잘못된 분기, 빠진 부작용, 잘못된 인자, 경계 조건, 깨진 계약(contract) 중 하나를 잡아낼 때 존재 가치가 있습니다.

**기대값은 독립적으로 도출하세요.** 리터럴과 직접 확인한 픽스처를 사용하세요 — 리터럴 `want` 값을 쓰는 테이블 기반 테스트가 선호되는 형태입니다. 검증 대상 코드(또는 그 헬퍼)로 계산한 기대값은 그 코드가 무엇을 하든 항상 통과합니다.

```python
# ❌ 거울 단언 — 같은 빌더로 양쪽을 계산 — 항상 참
expected = buildSearchQuery({"tag": "urgent"})
self.assertEqual(buildSearchQuery({"tag": "urgent"}), expected)

# ✅ 직접 도출한 리터럴
self.assertEqual(buildSearchQuery({"tag": "urgent"}), 'tag:"urgent"')
```

**변경 감지기(change detector)를 만들지 마세요.** 의도된 결정만 실패하게 만드는 테스트 — 상수값, 정확한 메시지 문구, 내부 구조 — 는 재설계 때마다 울리고 버그 앞에서는 잠듭니다. 결정에 의존하는 *동작*을 테스트하세요: `self.assertEqual(MAX_RETRIES, 5)`가 아니라 "실패한 호출은 5번 재시도되고 6번째 시도는 일어나지 않는다"를 검증하세요.

**동작을 테스트하세요, 텍스트가 아니라.** 스크립트나 스킬, 설정이 정확한 한 줄을 포함하는지 단언하는 것은 소스가 소스라는 것만 증명합니다. 스크립트는 통제된 입력으로 실행하고 출력/부작용/종료 코드를 단언하세요.

**여러분의 코드를 테스트하세요, 프레임워크가 아니라.** 코드가 경계에서 맺는 계약(등록하는 라우트, 내보내는 쿼리, 만드는 페이로드)을 테스트하세요. 업스트림 동작은 그 메인테이너의 테스트 몫입니다(대표적인 예: 여러분의 라우터가 등록된 핸들러를 호출하는지 단언하는 것 — 그건 프레임워크의 테스트지 여러분의 테스트가 아닙니다). 업스트림 동작이 정말 예상 밖이었다면, 그 가정을 이름 붙인 좁은 특성화(characterization) 테스트 하나만 작성하세요. 같은 경계 원칙이 코드 내부에도 적용됩니다: 생성자, getter, 상수, 단순 위임은 검증/정규화/기본값 설정/유도/강제/부작용을 일으킬 때만 테스트할 가치가 있습니다 — 그렇지 않으면 그것에 의존하는 첫 번째 소비자-가시적 결과를 단언하세요.

### 게이트 함수 (깨짐의 이름 대기)

```text
테스트 본문을 쓰기 전에:
  이 테스트를 실패하게 만들 프로덕션 코드 변경의 이름을 댈 수 있는가.

  하나도 댈 수 없다면            → 관찰 가능한 동작 중심으로 재설계
  "소스 텍스트가 바뀌었다"        → 산출물을 실행하고 그 효과를 단언
  의도된 결정만 해당한다면        → 변경 감지기다; 그 결정에 의존하는 동작을 테스트

  기대값이 검증 대상 코드 없이 도출되었는지 확인하라.
  만약 그 코드의 로직/헬퍼를 재사용한다면:
    리터럴이나 직접 확인한 픽스처로 바꿔라
```

## 원칙 2: 진짜 대상을 검증하라

**mock은 단언할 자격이 없습니다.** mock 단언은 mock이 존재하면 통과하고 없으면 실패합니다 — 그 컴포넌트에 대해서는 아무것도 말해주지 않습니다. 진짜 컴포넌트의 동작을 단언하세요. mock이 검증 대상이라면, mock을 풀거나 그 단언을 지우세요.

```python
# ✅ 진짜 동작 검증
self.assertIsNotNone(page.find(role="navigation"))

# ❌ mock 존재 여부 검증
self.assertIsNotNone(page.find(testid="sidebar-mock"))
```

**직접 물어야 할 질문:** "우리가 지금 mock의 동작을 테스트하고 있는 건 아닌가?"

**올바른 수준에서 mock하세요.** 진짜 메서드의 모든 부작용을 먼저 파악한 뒤, 느리거나 외부적인 연산만 mock하고 테스트가 의존하는 나머지는 진짜로 남기세요. 확신이 없으면 먼저 진짜 구현으로 테스트를 실행해 실제로 무엇이 필요한지 관찰하세요.

```python
# ❌ mock이 중복 탐지가 읽어야 할 설정 쓰기를 삼켜버림
@patch("myapp.ToolCatalog.discoverAndCacheTools", return_value=None)
def testSomething(self, mockDiscover):
    ...

# ✅ 느린 서버 기동만 mock하고, 테스트가 의존하는 설정 쓰기는 진짜로 남김
@patch("myapp.MCPServerManager")
def testSomething(self, mockManager):
    ...
```

**더블(double)을 구체적으로 만드세요.** 인자, 호출 횟수, 순서가 계약의 일부라면 그것을 단언하세요 — 아무거나 받아주는 가짜는 아무것도 검증하지 못합니다. 각 분기(성공/오류/잘못된 형식)마다 별도 픽스처나 스파이를 주어, 틀린 분기가 기대값을 만족시키지 못하게 하세요.

**mock 데이터는 실제 구조를 완전히 반영하세요.** 실제로 존재하는 완전한 구조를 mock하세요 — 테스트가 읽는 필드만이 아니라 문서화된 모든 필드를요. 부분 mock은 하위 코드가 빠진 필드를 읽을 때 조용히 실패합니다: 테스트는 통과하는데 실제 통합은 깨집니다.

**프로덕션 클래스는 프로덕션 메서드만 가집니다.** 테스트만 필요로 하는 정리(cleanup)는 프로덕션 클래스의 `destroy()` 같은 메서드가 아니라 테스트 유틸리티에 둡니다. 자문하세요: 이 메서드가 테스트에서만 호출되는가? 이 클래스가 이 자원의 생명주기를 소유하는가? 답이 아니라면 → 테스트 유틸리티로.

**복잡한 mock보다 진짜 컴포넌트를 우선하세요.** mock 설정이 테스트 로직보다 커지거나, mock이 진짜 컴포넌트가 가진 메서드를 놓치거나, mock이 바뀔 때마다 테스트가 깨진다면, 진짜 컴포넌트를 쓰는 통합 테스트로 전환하세요. **직접 물어야 할 질문:** "여기서 정말 mock이 필요한가?"

### 게이트 함수 (진짜 대상 검증)

```text
mock이나 테스트 헬퍼를 추가하기 전에:
  진짜 메서드의 부작용을 나열하고, 테스트가 의존하는 것은 진짜로 남겨라
  — 느리거나 외부적인 그 아래 수준만 mock하라.

  mock 응답은 실제 구조를 완전히 반영해야 한다.

  테스트만 호출하는 메서드는 테스트 유틸리티에 둔다, 프로덕션 클래스가 아니라.

  mock 자체를 단언하려는가?
    mock을 풀거나 그 단언을 지워라.
```

## 테스트는 구현과 함께 완성된다

TDD 사이클 — 실패하는 테스트, 최소 구현, 리팩터링 — 이 바로 "완료"의 의미입니다. 그 동작이 필요로 하는 테스트만 만드세요: 사소한 코드와 사람이 읽는 산문은 테스트가 필요 없고, 절차를 만족시키기 위해서만 쓴 테스트는 영원히 유지보수 비용을 냅니다.

## 뮤테이션 체크

마무리하기 전, 프로덕션 코드를 머릿속으로 변형(mutate)해 보세요. 현실적인 변형마다 최소 하나의 테스트가 실패해야 합니다.

- 잘못된 상수나 인자
- 잘못된 분기 처리
- 빠진 상태 변경이나 부작용
- 빈 값이나 기본값 반환
- 0, 빈 값, None, 권한 없음, 잘못된 형식에 대한 검증 누락

아무것도 잡지 못하는 변형은 그 동작이 보호되지 않고 있거나, 테스트가 항진명제(tautology)라는 뜻입니다.

## 빠른 참고

| 상황 | 할 일 |
| --- | --- |
| 아무 테스트나 작성할 때 | 그것이 잡는 깨짐의 이름을 대라 — 버그이지 결정이 아니다 |
| 기대값을 만들 때 | 손으로 도출하라; 검증 대상 코드로는 절대 만들지 마라 |
| 스크립트/문서를 테스트할 때 | 실행하라 / 소비자를 통해 압박 테스트하라; 소스 텍스트를 grep하지 마라 |
| 의존성 테스트에 손이 갈 때 | 그들의 문서화된 메커니즘이 아니라 여러분의 경계 계약을 테스트하라 |
| mock된 요소를 단언하려 할 때 | 진짜 컴포넌트를 테스트하거나, mock을 풀어라 |
| 메서드를 mock하려 할 때 | 부작용을 먼저 파악하라; 느리거나 외부적인 수준만 mock하라 |
| mock 응답을 만들 때 | 실제 구조를 완전히 반영하라 |
| 테스트만 쓰는 정리 코드가 필요할 때 | 테스트 유틸리티에 두어라 |
| mock 설정이 부풀어 오를 때 | 진짜 컴포넌트를 쓰는 통합 테스트로 전환하라 |
| 테스트 파일을 마칠 때 | 뮤테이션 체크를 실행하라 |

## 경고 신호

- 준비(setup)와 단언이 같은 객체를 공유해 동등함이 보장됨
- 테스트가 패닉/크래시/셀렉터 실패로만 실패할 수 있음
- 의도적 변경마다 항상 실패하고, 우발적 손상에는 절대 실패하지 않음
- 기대값이 루프/빌더/헬퍼 뒤에 숨어 있음
- 테스트가 소스 텍스트를 grep하거나, 제거된 심볼이 계속 없는지만 확인함
- 프레임워크만 남아도 여전히 통과할 테스트임
- 부작용이나 결과를 확인하지 않고 커버리지만을 위해 존재하는 테스트임
- `*-mock` 테스트 ID를 확인하거나, mock을 제거하면 실패하는 단언
- 테스트 파일에서만 호출되는 메서드
- mock 설정이 테스트의 절반을 넘거나, 왜 mock이 필요한지 설명할 수 없음
- "혹시 몰라서" mock하는 경우

## 이 프로젝트에서 추가로 요구하는 것

모든 테스트 함수는 위 원칙을 만족시키는 것에 더해, `test-annotation.md`의 형식(사용한 기법, 긍정/부정 케이스 여부, Doxygen 형식의 목적 설명)을 docstring에 반드시 포함해야 합니다.
