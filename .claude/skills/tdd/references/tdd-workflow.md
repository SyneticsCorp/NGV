# TDD 절차 — Iron Law와 Red-Green-Refactor

출처: [obra/superpowers](https://github.com/obra/superpowers) `skills/test-driven-development/SKILL.md`를 한국어로 옮기고 Python 3.12 + `unittest`로 각색했습니다.

## 핵심 원칙

테스트를 먼저 작성한다. 실패하는 것을 직접 확인한다. 그 다음 통과시키는 최소한의 코드를 작성한다.

**핵심 원칙:** 테스트가 실패하는 것을 직접 보지 않았다면, 그 테스트가 올바른 것을 검증하는지 알 수 없다.

**규칙의 문구를 어기는 것은 규칙의 취지를 어기는 것이다.**

## 언제 사용하는가

**항상:**

- 신규 기능
- 버그 수정
- 리팩터링
- 동작 변경

**예외(사용자에게 먼저 확인):**

- 버리는 프로토타입
- 자동 생성 코드
- 설정 파일

"이번만 TDD를 건너뛰자"는 생각이 든다면 멈추세요. 그건 합리화입니다.

## Iron Law (절대 규칙)

```text
실패하는 테스트 없이는 프로덕션 코드를 작성하지 않는다
```

테스트보다 코드를 먼저 썼다면? 지우고 다시 시작합니다.

**예외 없음:**

- "참고용"으로 남겨두지 않는다
- 테스트를 쓰면서 그 코드를 "적당히 손봐서" 재사용하지 않는다
- 쳐다보지 않는다
- 지운다는 건 진짜로 지운다는 뜻이다

테스트로부터 새로 구현합니다. 예외는 없습니다.

## Red-Green-Refactor 사이클

```text
RED(실패하는 테스트 작성) → 올바른 이유로 실패하는지 확인
  → GREEN(최소 구현) → 통과 확인(다른 테스트도 전부 통과)
  → REFACTOR(정리, 초록 상태 유지) → 다음 테스트로
```

### RED — 실패하는 테스트 먼저 작성

기대하는 동작 하나를 보여주는 최소한의 테스트를 작성합니다. `test-annotation.md`의 형식(기법/긍정·부정/Doxygen 목적)을 이 시점부터 함께 채웁니다.

**좋은 예:**

```python
class TestRetryOperation(unittest.TestCase):
    def testRetriesFailedOperationThreeTimes(self):
        """!
        @brief 연산이 두 번 실패해도 세 번째 시도에서 성공하면 결과를 반환한다.
        @technique 상태전이 테스트 — 실패→실패→성공 순서에 따른 재시도 횟수 검증
        @case Positive — 정상적으로 재시도 후 성공하는 경로
        @breaks retryOperation이 최대 재시도 횟수를 채우지 않고 조기 포기하는 회귀
        """
        attempts = 0

        def operation():
            nonlocal attempts
            attempts += 1
            if attempts < 3:
                raise RuntimeError("fail")
            return "success"

        result = retryOperation(operation)

        self.assertEqual(result, "success")
        self.assertEqual(attempts, 3)
```

명확한 이름, 실제 동작을 검증, 한 가지만 검증합니다.

**나쁜 예:**

```python
def testRetryWorks(self):
    mock = MagicMock(side_effect=[RuntimeError(), RuntimeError(), "success"])
    retryOperation(mock)
    self.assertEqual(mock.call_count, 3)
```

이름이 모호하고, 실제 코드가 아니라 mock의 호출 여부만 검증합니다(`writing-good-tests.md`의 "Mock at the right level" 위반).

**요구사항:**

- 동작 하나만
- 명확한 이름
- 실제 코드 사용(불가피한 경우가 아니면 mock 금지)

### RED 검증 — 실패를 직접 확인

**필수. 절대 건너뛰지 않습니다.**

```bash
python -m unittest <테스트모듈> -v
```

다음을 확인합니다:

- 테스트가 실패하는가(에러가 아니라 실패)
- 실패 메시지가 기대한 내용인가
- 기능이 없어서 실패하는가(오타 때문이 아니라)

**테스트가 통과한다면?** 이미 존재하는 동작을 테스트하고 있는 것입니다. 테스트를 고치세요.

**테스트가 에러를 낸다면?** 에러를 고치고, 올바르게 실패할 때까지 다시 실행하세요.

### GREEN — 최소 구현

테스트를 통과시키는 가장 단순한 코드를 작성합니다.

**좋은 예:**

```python
async def retryOperation(fn):
    for i in range(3):
        try:
            return await fn()
        except Exception:
            if i == 2:
                raise
```

딱 통과할 만큼만.

**나쁜 예:**

```python
async def retryOperation(fn, maxRetries=3, backoff="linear", onRetry=None):
    # YAGNI — 아직 필요하지 않은 기능
    ...
```

과잉 설계입니다.

기능을 추가하거나, 다른 코드를 리팩터링하거나, 테스트 범위를 넘어 "개선"하지 않습니다.

### GREEN 검증 — 통과를 직접 확인

**필수.**

```bash
python -m unittest <테스트모듈> -v
```

다음을 확인합니다:

- 테스트가 통과하는가
- 다른 테스트도 여전히 통과하는가
- 출력이 깨끗한가(에러, 경고 없음)

**테스트가 실패한다면?** 코드를 고치세요, 테스트를 고치지 마세요.

**다른 테스트가 실패한다면?** 지금 바로 고치세요.

### REFACTOR — 정리

Green 상태에서만 수행합니다:

- 중복 제거
- 이름 개선
- 헬퍼 추출

테스트는 계속 초록으로 유지합니다. 동작을 추가하지 않습니다. 정리가 끝나면 `quality-gates.md`의 품질 게이트를 실행합니다.

### 반복

다음 기능을 위한 다음 실패하는 테스트로 넘어갑니다.

## 테스트 파일 위치/명명 규칙 (이 프로젝트)

- 테스트 파일: `test_<대상 모듈>.py` (프로젝트에 이미 다른 관례가 있으면 그것을 따릅니다 — Glob으로 기존 `test_*.py`/`tests/` 구조를 먼저 확인하세요).
- 테스트 메서드명: `test<시나리오>` 형태의 camelCase, 3자 이상(CLAUDE.md 네이밍 규칙 적용) — 위 예시의 `testRetriesFailedOperationThreeTimes` 참고.
- 하나의 테스트 클래스는 하나의 구현 단위(`IU-NNNN`, `detailed-design` 스킬)에 대응시키는 것을 기본으로 합니다.
- 전체 실행: `python -m unittest discover -s <테스트 디렉터리> -p "test_*.py" -v`. 프로젝트에 테스트 디렉터리 구조가 아직 없다면 임의로 만들지 말고, `detailed-design`의 13장(구현 경계)이나 사용자에게 위치를 확인하세요.

## 흔한 합리화와 그 실체

| 변명 | 실체 |
| --- | --- |
| "너무 단순해서 테스트할 필요 없다" | 단순한 코드도 깨진다. 테스트는 30초면 된다. |
| "나중에 테스트하겠다" | 나중에 쓴 테스트는 바로 통과한다 — 아무것도 증명하지 못한다는 뜻이다. 잘못된 것을 테스트하거나, 동작 대신 구현을 테스트하거나, 잊어버린 경계 조건을 놓칠 수 있다. 실패를 직접 본 적이 없으니 버그를 잡을 수 있다는 증거가 없다. |
| "나중에 써도 목적은 같다(형식이 아니라 정신이 중요하다)" | 나중에 쓴 테스트는 "이게 뭘 하나?"에 답하고, 먼저 쓴 테스트는 "이게 뭘 해야 하나?"에 답한다. 나중에 쓴 테스트는 이미 짜놓은 코드에 편향되어, 기억나는 케이스만 확인하고 발견했을 케이스는 놓친다. |
| "이미 수동으로 테스트해봤다" | 수동 테스트는 즉흥적이다: 무엇을 확인했는지 기록이 없고, 코드가 바뀌면 재실행할 방법이 없고, 압박 속에서 케이스를 빠뜨리기 쉽다. |
| "지운 코드가 아깝다" | 매몰비용 오류다 — 그 시간은 이미 쓴 것이다. 진짜 선택지는: TDD로 다시 짜기(높은 신뢰) vs 그대로 두고 테스트만 나중에 붙이기(낮은 신뢰, 버그 가능성). 못 믿는 코드를 유지하는 게 낭비다. |
| "참고용으로 남기고 테스트부터 쓰겠다" | 결국 그 코드를 "적당히 손봐서" 쓰게 된다. 그건 나중에 테스트하는 것이다. 지운다는 건 진짜로 지운다는 뜻이다. |
| "먼저 탐색이 필요하다" | 좋다. 탐색 코드는 버리고 TDD로 시작하라. |
| "테스트하기 어려운 건 설계가 불분명해서다" | 테스트의 목소리를 들어라. 테스트하기 어렵다는 건 쓰기도 어렵다는 뜻이다. |
| "TDD는 나를 느리게 만든다" | TDD가 오히려 실용적인 길이다: 커밋 전에 버그를 잡고, 회귀를 막고, 두려움 없이 리팩터링하게 해준다. "실용적" 지름길은 결국 프로덕션에서 디버깅하는 것 — 더 느리다. |
| "기존 코드에는 테스트가 없다" | 지금 개선하고 있으니, 기존 코드에도 테스트를 추가하라. |

## 레드 플래그 — 멈추고 다시 시작

- 테스트보다 코드가 먼저
- 구현 후에 테스트
- 테스트가 바로 통과함
- 왜 실패했는지 설명할 수 없음
- 테스트를 "나중에" 추가함
- "이번만"이라고 합리화함
- "이미 수동으로 테스트했다"
- "나중에 써도 목적은 같다"
- "형식이 아니라 정신이 중요하다"
- "참고용으로 남기겠다", "기존 코드를 적당히 활용하겠다"
- "이미 X시간 썼는데 지우는 건 낭비다"
- "TDD는 교조적이다, 나는 실용적으로 하는 것이다"
- "이번 경우는 다르다..."

**이 중 하나라도 해당하면: 코드를 지우고 TDD로 다시 시작합니다.**

## 완료 체크리스트

작업을 완료로 표시하기 전에:

- [ ] 새 함수/메서드마다 테스트가 있다
- [ ] 구현 전에 각 테스트가 실패하는 것을 직접 확인했다
- [ ] 각 테스트가 기대한 이유로 실패했다(오타가 아니라 기능 부재)
- [ ] 각 테스트를 통과시키는 최소한의 코드를 작성했다
- [ ] 모든 테스트가 통과한다
- [ ] 출력이 깨끗하다(에러, 경고 없음)
- [ ] 테스트가 실제 코드를 사용한다(불가피한 경우만 mock)
- [ ] 경계 조건과 오류 케이스를 다뤘다
- [ ] 모든 테스트 함수에 `test-annotation.md` 형식(기법/긍정·부정/Doxygen 목적)이 있다
- [ ] `quality-gates.md`의 5개 품질 게이트를 통과했다

체크박스를 전부 채울 수 없다면 TDD를 건너뛴 것입니다. 다시 시작하세요.

## 막혔을 때

| 문제 | 해결 |
| --- | --- |
| 테스트를 어떻게 짤지 모르겠다 | 원하는 API를 먼저 써본다. 단언(assert)문부터 쓴다. 사용자에게 물어본다. |
| 테스트가 너무 복잡하다 | 설계가 너무 복잡하다는 신호다. 인터페이스를 단순화하라. |
| 모든 걸 mock해야 한다 | 코드가 너무 결합되어 있다는 신호다. 의존성 주입을 사용하라. |
| 테스트 준비 코드가 거대하다 | 헬퍼로 추출하라. 그래도 복잡하면 설계를 단순화하라. |

## 디버깅과의 연계

버그를 발견했나요? 그 버그를 재현하는 실패하는 테스트를 먼저 작성하세요. TDD 사이클을 따르세요. 테스트가 수정을 증명하고 회귀를 막습니다.

테스트 없이 버그를 고치지 않습니다.

## 최종 규칙

```text
프로덕션 코드 → 먼저 실패한 테스트가 존재해야 한다
그렇지 않다면 → TDD가 아니다
```

사용자의 명시적 허락 없이는 예외가 없습니다.
