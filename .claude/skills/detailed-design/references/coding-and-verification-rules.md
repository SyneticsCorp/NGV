# 코딩 및 검증 규칙 (TPL-SWE3-001 §11 대응)

TPL-SWE3-001 11장은 "코딩 표준, 정적분석, 단위검증, 커버리지와 리뷰 기준"을 요구하지만 특정 표준(예: MISRA)을 지정하지 않습니다. 지어내지 말고 아래 순서로 확인/제안하세요.

## 1. 프로젝트가 이미 채택한 규칙이 있는지 확인

Glob/Grep으로 `.pylintrc`, `pyproject.toml`, `setup.cfg`, `.flake8`, `mypy.ini`, `CONTRIBUTING.md`, 코딩 규칙 문서 등을 먼저 찾아보세요. 있다면 그 내용을 11장에 그대로 인용하고 지어내지 않습니다.

## 2. 없다면 제안 (Python 프로젝트로 추정되는 경우)

`TPL-SBOM-001`이 "Python 의존성"을 전제로 하는 것으로 보아 이 프로젝트는 Python을 사용할 가능성이 있습니다(확정 아님 — 실제 소스 구조로 확인하세요). Python이 맞다면 아래를 기본 제안으로 사용하고 사용자 확인을 받으세요.

| 항목 | 제안 |
| --- | --- |
| 코딩 표준 | PEP 8 (스타일), 타입 힌트(PEP 484) 사용 |
| 정적분석 | `ruff` 또는 `flake8`(린트), `mypy`(타입 검사) |
| 복잡도 기준 | 함수당 순환복잡도(cyclomatic complexity) 상한을 프로젝트 리스크 수준에 맞게 설정(예: 10) — 임의로 정하지 말고 사용자와 합의 |
| 단위검증 기법 | `pytest` 기반 단위 테스트 |
| 커버리지 목표 | 구문(statement) 커버리지 목표를 우선 제안하고, 안전 관련 단위는 분기(branch) 커버리지까지 상향 검토 — ASIL이 높을수록 더 엄격한 커버리지가 기대됨(`iso26262-aspice-alignment.md`) |
| 리뷰 기준 | 코드 리뷰 체크리스트(계약 일치, 오류 처리 누락, 명명 규칙) — 리뷰 기록은 A-SPICE PA 2.2(작업 산출물 관리)의 근거가 됨(`aspice-auditor` 스킬과 연계) |

다른 언어가 확인되면 그 언어의 실제 관례(예: C/C++이면 MISRA C 여부를 사용자에게 확인)를 지어내지 말고 질문하세요.

## 3. 실행 가능성 검증 (필수)

`requirements-analysis`의 `nfr-iso25010.md`와 동일한 원칙을 적용합니다 — 아래에 해당하면 다시 작성하세요.

- 프로젝트에 실제로 설치/실행할 수 없는 도구를 전제로 한 기준.
- 판정 기준(수치/체크리스트)이 없는 "충분히 안전하게 작성한다" 식의 기준.
- 접근 권한이 없는 코드(서드파티 바이너리 등)에 대한 커버리지 요구.

## 4. 11장에 기록할 내용

1. 채택한(또는 확인된) 코딩 표준과 그 근거(기존 설정 파일 인용 또는 제안 후 합의).
2. 정적분석 도구와 통과 기준.
3. 단위검증 기법과 커버리지 목표(ASIL/리스크 수준별로 다르면 그 근거).
4. 리뷰 기준과 리뷰 기록 보관 방법(추후 `aspice-auditor`가 PA 2.2 근거로 확인할 수 있게).
