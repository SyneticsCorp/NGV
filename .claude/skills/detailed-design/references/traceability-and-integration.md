# 양방향 추적성 (TPL-SWE3-001 §12/§14, TPL-TRC-001 연계)

상세설계는 추적 사슬의 중간 지점입니다: 아키텍처 요소(`ARC-NNNN`) ← 만족 → 구현 단위(`IU-NNNN`) → 검증 → 단위시험(SWE.4). 이 문서는 `requirements-analysis`의 `traceability.md`(`TPL-TRC-001`)와 짝을 이룹니다 — 별도 매트릭스를 새로 만들지 않고 같은 산출물(`ENG-TRC-001`)을 갱신합니다.

## TPL-TRC-001 "Detailed Design" 열에 기록할 값

- `IU-NNNN` (구현 단위 ID). 함수 단위까지 추적이 필요하면 `IU-NNNN.함수명`까지 기록합니다.
- 하나의 `SW Req`/`Architecture` 항목에 여러 구현 단위가 연결될 수 있습니다 — 이 경우 해당 행에 쉼표로 나열하거나 행을 복제합니다(매트릭스 관례는 `requirements-analysis`의 `traceability.md` 유지 규칙을 그대로 따름).

## 12장(단위와 요구사항 할당)에 기록할 내용

각 구현 단위에 대해:

| 필드 | 설명 |
| --- | --- |
| 구현 단위 | `IU-NNNN` |
| 대응 아키텍처 요소 | `ARC-NNNN` (만족 관계) |
| 대응 소프트웨어 요구사항 | `SWR-NNNN` (하나 이상) |
| 단위시험 상태 | 아직 SWE.4 산출물이 없으면 "미착수", 있으면 테스트 케이스 ID |

## 14장(추적성)에 기록할 내용

상세설계서 자체에는 요약만 남기고("전체 추적성은 `ENG-TRC-001` 참조"), 실제 매트릭스는 xlsx 산출물에서 관리합니다 — `requirement-schema.md`(requirements-analysis)의 11장 처리 방식과 동일합니다.

## 유지 규칙

1. 구현 단위를 추가/변경/폐기할 때마다 같은 작업 내에서 `ENG-TRC-001`의 `Detailed Design` 열을 함께 갱신합니다.
2. 아키텍처 요소나 요구사항과 연결되지 않는 구현 단위(고아)가 발견되면 그대로 두지 말고 갭으로 보고합니다 — 왜 필요한지 근거가 없는 단위는 범위(`design-schema.md` 13장 구현 경계)에서 벗어난 것일 수 있습니다.
3. 요구사항이나 아키텍처 요소가 변경되면, 그와 연결된 모든 구현 단위에 "재확인 필요" 표시를 남깁니다(영향 분석).
4. `detailed-design-diagrams.md`의 다이어그램, `design-schema.md`의 본문, `ENG-TRC-001`의 매트릭스 — 이 세 곳의 ID와 관계는 항상 일치해야 합니다.
