# 기본 요구사항 스키마 (템플릿 미반영 시)

지정 템플릿이 반영되기 전까지 모든 요구사항 항목은 아래 필드를 갖춰야 합니다. 템플릿이 제공되면 필드는 유지한 채 표현 형식만 템플릿에 맞춰 재구성합니다.

## 공통 필드

| 필드 | 설명 |
|---|---|
| ID | 고유 식별자 (아래 ID 체계 참고) |
| 제목 | 한 줄 요약 |
| 설명 | EARS 패턴을 따르는 요구사항 문장 (`clarity-and-consistency.md`) |
| 유형 | 기능(Functional) / 비기능(Non-Functional) |
| 출처 | 이해관계자 요구, 상위 요구사항, 안전목표 등 근거 |
| ASIL | 안전 관련 요구사항인 경우 ISO 26262 ASIL 등급(QM/A/B/C/D), 해당 없으면 "N/A" |
| 우선순위 | 필수/권장/선택 등 |
| 상태 | 초안 / 검토중 / 승인 / 변경됨 |
| 추적 링크 | 상위·하위 산출물과의 양방향 링크 (`traceability.md`) |

## 기능 요구사항 추가 필드

| 필드 | 설명 |
|---|---|
| 관련 다이어그램 | 이 요구사항을 표현하는 UML/SysML 다이어그램 참조 (`uml-sysml-diagrams.md`) |
| 트리거/사전조건 | EARS 패턴의 트리거 또는 상태 조건 |
| 예상 동작 | 시스템이 수행해야 하는 반응 |

## 비기능 요구사항 추가 필드

| 필드 | 설명 |
|---|---|
| ISO 25010 특성/부특성 | `nfr-iso25010.md` 참고 |
| 정량적 기준 | 측정 가능한 수치/조건 |
| 검증방안 | 기법(시험/분석/검사/시연) + 합격 기준 + 필요 도구/환경. 실행 불가능한 방법 금지 |

## ID 체계

`REQ-<영역>-<유형>-<일련번호>` 형식을 기본으로 사용합니다.

- 영역: `SYS`(시스템), `SW`(소프트웨어), `HW`(하드웨어) 등 프로젝트 구조에 맞게 조정.
- 유형: 기능은 `FUNC`, 비기능은 `NFR`(필요 시 ISO 25010 특성 약어를 덧붙여도 됨, 예: `NFR-SEC`, `NFR-PERF`).
- 일련번호: 4자리, 0으로 채움 (예: `0001`).

예시: `REQ-SYS-FUNC-0012`, `REQ-SW-NFR-SEC-0003`.

- ID는 한 번 부여되면 재사용하거나 변경하지 않습니다. 요구사항이 폐기되어도 ID는 "폐기됨" 상태로 남기고 재사용하지 않습니다(추적성 훼손 방지).
- 이미 프로젝트에서 사용 중인 ID 체계가 있다면 이를 우선 따르고, 이 문서의 체계는 참고용으로만 사용하세요.
