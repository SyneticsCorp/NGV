# 명확성(Clarity)과 일관성(Consistency) 확보

## 명확성 — EARS 패턴

요구사항 문장이 사람마다 다르게 해석되지 않도록, 모든 요구사항 설명은 EARS(Easy Approach to Requirements Syntax) 패턴 중 하나를 따라 작성합니다. 각 패턴은 "언제/어떤 조건에서, 무엇이, 무엇을 해야 한다"를 명시적으로 드러냅니다.

| 패턴 | 형식 | 사용 상황 |
|---|---|---|
| 유비쿼터스(Ubiquitous) | `<시스템>은 <행동>을 한다.` | 항상 성립하는 요구사항 |
| 이벤트 기반(Event-driven) | `<트리거>가 발생하면, <시스템>은 <반응>을 한다.` | 특정 이벤트에 대한 반응 |
| 상태 기반(State-driven) | `<상태>인 동안, <시스템>은 <행동>을 한다.` | 특정 상태에서만 성립 |
| 원치 않는 동작(Unwanted behavior) | `<원치 않는 조건>이 발생하면, <시스템>은 <대응>을 한다.` | 오류/예외 처리, 안전 요구사항에 특히 유용 |
| 선택적 기능(Optional feature) | `<기능>이 있는 경우, <시스템>은 <행동>을 한다.` | 옵션/변형 기능 |
| 복합(Complex) | 위 패턴을 조합 | 여러 조건이 얽힌 경우 |

작성 시 금지 사항:

- "빠르게", "적절히", "가능한 한", "사용자 친화적으로" 등 측정 불가능한 모호한 표현을 단독으로 사용하지 않습니다 — 반드시 정량적 기준(예: "200ms 이내")이나 구체적 판정 기준을 함께 명시합니다.
- 한 문장에 서로 다른 여러 요구사항을 묶지 않습니다(요구사항 하나당 검증 가능한 주장 하나).
- 수동태나 "~해야 할 수도 있다"처럼 의무 수준이 불분명한 표현을 피하고, "~해야 한다(shall)" 수준으로 명확한 의무를 표현합니다.

## 일관성 — 산출물 마무리 전 자체 점검 체크리스트

요구사항 산출물을 마무리하기 전에 아래를 점검합니다.

1. **용어 일관성** — 동일한 개념을 서로 다른 용어로 부르고 있지 않은가? (예: "사용자"와 "운영자"를 혼용) 프로젝트에 용어집이 있다면 이를 따르고, 없다면 이번 산출물 내에서 용어를 통일하고 처음 등장 시 정의합니다.
2. **중복/상충 여부** — 동일 대상에 대해 서로 다른 수치·조건을 요구하는 요구사항이 있는가? 발견하면 임의로 하나를 지우지 말고 상충 사실을 명시하고 사용자에게 확인을 요청합니다.
3. **ID/필드 형식 일관성** — 모든 요구사항이 동일한 ID 체계와 필드 구성(`requirement-schema.md` 또는 지정 템플릿)을 따르는가?
4. **EARS 패턴 준수 여부** — 모든 요구사항 설명이 위 패턴 중 하나로 작성되었는가? 벗어난 문장이 있으면 재작성합니다.
5. **추적 링크 존재 여부** — 모든 요구사항에 최소 하나의 상위(출처) 링크가 있는가? 하위 산출물이 이미 존재하는데 링크가 없는 요구사항(고아)이 있는가?
6. **검증방안 실행 가능성** — 모든 비기능 요구사항의 검증방안이 실제로 수행 가능한가(`nfr-iso25010.md` 기준)?
