# 인터페이스 정의와 통합 순서 (TPL-SWE2-001 §6/§11 대응)

## 인터페이스 정의 규칙 (필수)

**모든 컴포넌트 간 통신은 명시적으로 정의된 인터페이스를 통해서만 이루어져야 합니다.** 전역 변수 공유, 다른 컴포넌트의 내부 자료구조 직접 접근, 문서화되지 않은 암묵적 프로토콜은 허용하지 않습니다(`design-principles.md`의 내용 결합/공통 결합 금지와 동일한 이유).

TPL-SWE2-001 6장(인터페이스 명세)은 아래 필드를 요구합니다. 이 필드 구성을 그대로 사용하세요(임의로 필드를 추가/삭제하지 않습니다).

| 필드 | 설명 |
| --- | --- |
| 인터페이스 ID | 고유 식별자, `IF-<번호>` (requirements-analysis 스킬의 `IF-NNNN`과 동일 체계 사용) |
| 제공자 | 이 인터페이스를 제공(provide)하는 컴포넌트 |
| 사용자 | 이 인터페이스를 요구(require)하는 컴포넌트 |
| 데이터 | 오가는 데이터 항목(타입/단위/범위) |
| 호출 조건 | 사전조건, 호출 방식(동기/비동기, 주기/이벤트) |
| 시간 제약 | 응답시간, 주기, 타임아웃 등 |
| 오류 계약 | 실패 시 반환값/오류 코드와 호출 측 처리 기대사항 |

- 6.1 내부 인터페이스(같은 시스템/서브시스템 내부 컴포넌트 간), 6.2 외부 인터페이스(다른 시스템/공급자/하드웨어와의 경계)로 나눠 기술합니다.
- 각 인터페이스는 이를 만족(satisfies)하는 요구사항 ID(`requirements-analysis`의 `SWR-NNNN`)와 연결해 12장(요구사항 할당)·14장(추적성)에서 참조 가능하게 합니다.

컴포넌트를 분해한 뒤, 서로 통신이 필요한 컴포넌트 쌍마다 위 표를 채운 인터페이스가 존재하는지 확인하세요. 존재하지 않으면 설계가 끝난 것이 아닙니다.

## 통합 순서 정의 (TPL-SWE2-001 §11 통합 전략)

11장은 아래 필드를 요구합니다.

| 필드 | 설명 |
| --- | --- |
| 통합 단위 | 이번 단계에서 통합되는 컴포넌트(들) |
| 순서 | 몇 번째 단계인지 |
| 인터페이스 검증 | 이 단계에서 검증할 인터페이스 ID와 검증 방법 |
| 스텁 또는 드라이버 | 아직 통합되지 않은 의존 컴포넌트를 대신할 스텁/드라이버 필요 여부 |
| 회귀 범위 | 이 단계 통합으로 재검증이 필요한 기존 범위 |

절차:

1. 컴포넌트 간 의존성 그래프를 작성합니다(`architecture-diagrams.md` — Mermaid `graph`/`flowchart`).
2. **순환 의존성이 있으면 통합 순서를 정하기 전에 먼저 구조 문제로 보고하세요.** 순환 의존은 결합도 원칙 위반이며, 인터페이스 재설계(예: 이벤트 기반으로 전환, 공통 의존 대상을 별도 컴포넌트로 추출)로 해소해야 합니다.
3. 순환이 없다면 의존성이 적은(기반이 되는) 컴포넌트부터 상향식(bottom-up)으로 통합하는 것을 기본 전략으로 제안합니다.
4. 다음 경우에는 전략을 조정하고 그 근거를 "회귀 범위"/"인터페이스 검증" 칸에 문서화하세요.
   - 안전 필수(높은 ASIL) 컴포넌트를 조기에 검증해야 하는 경우 → 해당 경로를 우선 통합하고 나머지는 스텁/드라이버로 대체.
   - 외부 인터페이스(하드웨어, 공급자 컴포넌트)의 가용 시점이 늦는 경우 → 그 시점까지 인터페이스 스텁으로 대체하는 계획을 함께 명시.
5. 이 통합 순서는 SWE.4/SWE.5(단위·통합 시험)의 입력이 되므로, 근거 없이 순서만 나열하지 마세요.
