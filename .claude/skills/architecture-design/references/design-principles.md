# 설계 원칙 체크리스트 (응집도·결합도 / SOLID / 변경 유연성)

이 문서는 사용자가 **반드시** 요구한 "높은 응집도, 낮은 결합도"와 "SOLID 준수", "변경에 유연한 구조"를 실제로 점검하기 위한 체크리스트입니다. 형식적으로 언급만 하고 넘어가지 말고, 컴포넌트를 나눌 때마다 실제로 아래 기준으로 평가하세요.

`TPL-SWE2-001`에는 이 점검 결과를 위한 전용 장이 없으므로, 4장(컴포넌트 책임)·5장(정적 의존성)에 컴포넌트 분해 근거로 녹여 넣고, 필요하면 10장(품질 속성 분석)에 유지보수성/변경 용이성 평가로 요약하세요(`template-policy.md`).

## 응집도(Cohesion) — 높을수록 좋음

컴포넌트 하나가 하나의 명확한 책임/목적만 갖는지 평가합니다. 아래는 응집도가 높은 순서입니다(위로 갈수록 바람직함).

1. 기능적 응집(Functional) — 모든 요소가 하나의 잘 정의된 작업을 위해 함께 동작함.
2. 순차적 응집(Sequential) — 한 요소의 출력이 다음 요소의 입력이 됨.
3. 교환적 응집(Communicational) — 동일한 데이터를 다루는 요소들의 모음.
4. 절차적 응집(Procedural) — 특정 순서로 실행되어야 하지만 목적은 다른 요소들의 모음.
5. 시간적 응집(Temporal) — 같은 시점에 실행된다는 이유만으로 묶임(예: 초기화 루틴).
6. 논리적 응집(Logical) — 비슷한 범주라는 이유로만 묶임(예: "모든 입출력 처리").
7. 우연적 응집(Coincidental) — 특별한 관계 없이 묶임. **금지** — 발견 시 반드시 재분리.

컴포넌트를 나눌 때: 이름을 지어봤을 때 "그리고(and)"가 들어가면 응집도가 낮다는 신호입니다. 재검토하세요.

## 결합도(Coupling) — 낮을수록 좋음

컴포넌트 간 상호 의존 정도를 평가합니다. 아래는 결합도가 낮은 순서입니다(위로 갈수록 바람직함).

1. 데이터 결합(Data) — 필요한 데이터만 파라미터로 주고받음.
2. 스탬프 결합(Stamp) — 필요 이상의 구조체/객체 전체를 주고받음(일부 필드만 필요한데 전체 전달).
3. 제어 결합(Control) — 상대 컴포넌트의 내부 동작을 제어하는 플래그를 전달함.
4. 외부 결합(External) — 공유된 외부 형식/프로토콜/장치에 의존함.
5. 공통 결합(Common) — 전역 데이터를 공유함.
6. 내용 결합(Content) — 한 컴포넌트가 다른 컴포넌트의 내부를 직접 참조/수정함. **금지** — 인터페이스 경유로 반드시 재설계.

목표는 최소한 "데이터 결합" 수준을 유지하는 것이며, 공통 결합·내용 결합이 발견되면 반드시 인터페이스를 통한 통신으로 재설계하세요(`interface-and-integration.md`).

## SOLID 원칙 (컴포넌트/아키텍처 수준 적용)

| 원칙 | 아키텍처 수준 질문 |
| --- | --- |
| 단일 책임(SRP) | 이 컴포넌트가 변경되어야 할 이유가 하나뿐인가? 둘 이상이면 분리를 검토했는가? |
| 개방-폐쇄(OCP) | 새 기능 추가 시 기존 컴포넌트의 인터페이스/코드를 수정하지 않고 확장(새 구현체 추가)으로 대응 가능한가? |
| 리스코프 치환(LSP) | 동일 인터페이스의 다른 구현체로 교체해도 호출 측 동작이 깨지지 않는가? |
| 인터페이스 분리(ISP) | 인터페이스가 사용하지 않는 오퍼레이션까지 강제하지 않는가(거대 인터페이스를 여러 개로 쪼갤 여지는 없는가)? |
| 의존성 역전(DIP) | 상위 수준 컴포넌트가 하위 수준의 구체 구현이 아니라 추상(인터페이스)에 의존하는가? |

## 변경 유연성 체크리스트

- 예상되는 변경 시나리오(요구사항 변경, 하드웨어/플랫폼 교체, 규정 변경 등)를 나열하고, 각 시나리오가 몇 개의 컴포넌트에 영향을 주는지 추정합니다. 하나의 사소한 변경이 다수 컴포넌트에 파급되면 결합도가 높다는 신호이므로 경계를 재검토합니다.
- 변경 가능성이 높은 부분(예: 특정 하드웨어 의존, 외부 규격 의존, 정책성 로직)을 인터페이스 뒤로 격리했는지 확인합니다.
- 설정으로 대체 가능한 것을 코드에 하드코딩하지 않았는지 확인합니다.

## 마무리 점검

설계를 완료하기 전, 각 컴포넌트에 대해 "응집도가 낮은 신호(우연적/논리적 응집)"나 "결합도가 높은 신호(공통/내용 결합)"가 하나라도 있으면 재설계하고, 그 근거를 산출물에 남기세요.
